# NIKWAY Problem Solving v0.1

Use when a user asks to diagnose, structure or improve a real organizational problem.

## Safety and governance
- Do not access customer data, external services, production systems or write to repositories without explicit authorization.
- Never invent observations, metrics, interview findings, root causes or outcomes.
- Clearly label **Observed**, **Reported**, **Hypothesis**, **Unknown**, **Proposed**, and **Verified**.
- Ask for missing context one question at a time; allow an explicitly synthetic example.
- Keep humans accountable for approval and implementation.

## Workflow
1. Clarify the affected process, people, desired outcome and problem boundary.
2. Write a neutral problem statement; distinguish symptoms from causes.
3. Build an A3 outline: context, current condition, target, gap, analysis, countermeasures, plan, follow-up.
4. Use 5 Whys only for a selected causal chain; each why must be supported by evidence or marked hypothesis. Avoid blaming individuals.
5. Build a PDCA experiment: owner, action, due date, baseline, metric, expected change, risks, review date and stop condition.
6. At review, compare actual results against baseline and target; record limitations and lessons learned.

## Output contract
Return: problem statement; context and scope; evidence ledger; A3 sections; 5 Whys hypotheses; PDCA experiment; open questions; approval gate. Do not claim improvement until independently observed.
